## 面试官到底在考什么

**问断点续传**，不是想听"我调了 DownloadDependenciesAsync"。他想知道：
- 你知不知道续传的**粒度**（bundle 级 / 字节级）；
- 你懂不懂**缓存一致性**（下到一半的数据为什么不会被当成好资源）；
- 版本更新时旧缓存怎么失效。

**问消息流**，不是想听"用了 TCP + Protobuf"。他想知道：
- 一条消息从点击到屏幕上，**中间经过几次序列化、几次线程切换**；
- 多进程之间怎么**找到对的那个客户端**（这是分布式网关的核心难点）；
- 连接是"每个玩家一条"还是"两个进程一条"。

答这两个问题的分水岭：**能不能主动说出边界和取舍**。只说做了什么，听起来像照文档抄；说清"为什么这么做、代价是什么、再往下怎么做"，才像自己踩过。

# 问题一：热更新断点续传

## 30 秒版（先背这段，被打断也够用）

> 我的热更资源是 Addressables 管的，断点续传没有自己写，落在 Unity 的 AssetBundle 缓存上。
> 启动时先检查并更新 catalog，再用 `GetDownloadSizeAsync` 汇总"还没进缓存的 bundle"有多大。
> 10MB 下到 5MB 退出，已经落盘的 bundle 下次直接命中缓存，只补剩下的那部分。
>
> 但我要说清粒度：**这是 bundle 级的续传，不是字节级**。如果 5MB 那个点正好卡在某个大 bundle 中间，那个 bundle 会整个重下。
> 原因是 bundle 内部数据互相依赖，半截文件没法用；Unity 的 bundle 缓存也是原子写入，下完才生效，所以不会出现"半个资源被当成好资源"导致资源错乱。

## 2 分钟版（把链路讲完）

> 我这边热更分两条线：**代码热更**用 HybridCLR，**资源热更**用 Addressables。
> 资源这条的启动流程是 7 步：
>
> 1. `Addressables.InitializeAsync()` 初始化，加载本地 catalog；
> 2. `CheckForCatalogUpdates()` 比对远端 catalog 的 hash，有新版就 `UpdateCatalogs()`；
> 3. 加载热更进度窗口；
> 4. `GetDownloadSizeAsync("preload")` 算出还差多少字节；
> 5. 大于 0 就 `DownloadDependenciesAsync`，循环读 `GetDownloadStatus()` 刷进度条；
> 6. 加载 HybridCLR 的 AOT 元数据（`LoadMetadataForAOTAssembly`，`SuperSet` 模式）；
> 7. `Assembly.Load` 加载热更 dll，最后实例化 `GameLanuch` 进游戏。
>
> 断点续传能成立，靠的是两个东西：
> **一是 catalog 里记了每个 bundle 的 hash**，远端 URL 是"路径+bundle 名+hash"，缓存 key 带 hash，所以内容一变 hash 就变，旧缓存自动失效、不会误用；
> **二是 `GetDownloadSizeAsync` 本身就只统计"未缓存"的 bundle**，全部命中缓存时它返回 0，我直接跳过下载进游戏。
>
> 所以"下到 5MB 退出"这件事，对系统来说不是"续传一个 10MB 的文件"，而是"10 个 bundle 下完了 4 个半"。下次进来它只知道还差 5 个半的量。

## 追问预案

**Q：下到一半被杀进程，那个半截文件不会残留成脏数据吗？**
> 不会。Addressables 底层走 `UnityWebRequestAssetBundle`，bundle 是**下完才写入缓存并 commit** 的，没下完的不会进缓存索引。所以最坏情况只是"这次白下了"，不会出现"文件存在但内容不全"。

**Q：那你怎么知道该下多少？catalog 不是也要下载吗？**
> 对，catalog 本身就是第一个要更的东西。顺序必须是**先更 catalog、再算下载量**，因为新 bundle 的名字、hash、大小都写在 catalog 里，catalog 不更新你算出来的还是旧账。我代码里 `CheckForCatalogUpdates` 一定在 `GetDownloadSizeAsync` 之前。

**Q：如果我要做字节级续传呢？**
> 那要绕开 Addressables 的 bundle 机制，自己在 HTTP 层做三件事：
> 1. 用 `Range: bytes=<offset>-` 发请求，服务端要支持 `Accept-Ranges`；
> 2. 边收边追加写本地 `.part` 文件，把已下载偏移定期落到一个小 manifest 里；
> 3. 下完比对 hash/大小，通过再 rename 成正式文件。
> 要注意 UnityWebRequest 不暴露 Range/追加写的能力，得用 `HttpWebRequest` 或者自己封 socket。
> 我没在项目里做，因为资源是 bundle 切分的，一个 bundle 通常几百 KB 到几 MB，bundle 级重下的代价可以接受；真正需要字节级的是"整包 APK 更新"这种单个超大文件。

**Q：版本回滚怎么办？**
> catalog 换回旧版就行，因为缓存 key 带 hash，旧 bundle 如果还在缓存里就直接命中；不在就重新下。但要注意 Addressables 不会自动清掉新版本留下的孤儿 bundle，得主动调 `ClearDependencyCacheAsync` 或者按 `Caching` 的过期策略回收。

**Q：热更失败怎么处理？**
> 这是我这块做得不够的地方，我如实说：现在 `DownloadDependenciesAsync` 失败只打了一条 `LogError`，然后流程继续往下走加载 DLL，真机上会变成"资源缺了还硬进游戏"。正确做法是失败就停在热更页给重试按钮，或者至少不要继续往下走。这是我这版要补的。

## 两个必须知道的真实缺陷（别说漏嘴）

1. **`preload` 标签没配**。`Load.cs` 里用的是 `PreloadLabel = "preload"`，但工程里 Addressables 的标签表只有 `default`，没有任何分组挂 `preload`。结果是 `GetDownloadSizeAsync("preload")` 恒为 0，**下载分支实际走不到**。
   → 面试前要么把标签补上（在分组里加 `preload` 标签即可），要么话术改成"链路是按标签汇总依赖搭的，标签配置是联调阶段要补的"。
   → **不要说"我已经跑通了完整资源下载"**，被追问"那你怎么验证的"会翻车。

2. **下载失败继续往下走**。见上面 Q&A，主动承认比被问出来好。

# 问题二：消息流传输

面试官这句话其实是**三个问题**，必须分开答，混着答一定乱：

1. 客户端和服务端怎么建立连接？
2. 消息怎么送到 Unity 客户端？
3. 服务端和服务端之间怎么传、怎么找到对的人？

## 开场一句（定框架）

> 我这套是 **TCP 长连接 + Protobuf + 命令码路由**。
> 拓扑上客户端只连登录服一个口，登录服再作为客户端连中心服，中心服独占数据库。
> 一条消息的旅程可以分三层看：**连接层、编解码层、路由层**。

## 第一层：连接怎么建

> 客户端启动时 `NetClient` 用 `Socket.BeginConnect` 异步连 `127.0.0.1:10120`，连上后立刻 `BeginReceive` 挂起等待数据，全程异步、不阻塞主线程。
>
> 服务端 `NetServer` 先 `Bind` + `Listen(100)`，在一条后台线程上 `BeginAccept`；每 accept 到一个连接就 new 一个 `Session`，一个连接一个 Session，Session 里存 `SessionId` 和 socket，统一注册到 `SessionMgr` 里，靠 `Interlocked.Increment` 生成自增 Id 保证线程安全。
>
> **关键点：服务端之间不是每个玩家一条连接**。LoginServer 和 CenterServer 之间只有**一条**共享 TCP 长连接（`new NetClient(..., ClientType.LoginServer)` 单例），所有玩家的请求都复用这一条，靠包里的 `unity_session_id` 区分是谁。这样连接数从"玩家数×2"降到"玩家数+1"，代价是这条连接断了所有在线玩家一起断。

## 第二层：编解码（一条消息长什么样）

> 每帧的字节结构是：**2 字节长度 + 1 字节压缩标志 + 2 字节 CRC16 + N 字节 Protobuf**。
>
> - 长度在最前面，是为了解决 TCP 粘包/半包：收包缓冲里凑够 `msgLen+2` 才切一帧，切完把剩下的 `BlockCopy` 到缓冲区头部，再 `while` 循环继续切，一次 recv 里有多帧就一次消化完；不够就 break 等下一批数据。
> - body 超过 200 字节自动 GZip，小包不压，省 CPU。
> - CRC16 校验的是压缩后的 body，校验不过直接丢这一帧，不进业务。
>
> Proto 的外层是 `BasePackage{ proto_code, unity_session_id, gate_session_id, data }`，`data` 里才是具体业务包（`LoginReq`、`PositionSyncReq` 这些）。这样所有协议共享一个信封，中间层不用认识业务类型就能转发。

## 第三层：路由（消息怎么找到对的人）

**服务端 → 客户端方向：**

> 收包时 `Session.HandleCommand` 会打标：如果这条连接的对端是 LoginServer 或 GateServer，说明它是替某个 Unity 玩家转发的，就把它自己的 `SessionId` 写进 `basePackage.UnitySessionId`。
>
> 回包时反过来查：CenterServer 处理完把同一个 `BasePackage` 原样发回来（`UnitySessionId` 字段跟着回），LoginServer 收到后 `SessionMgr.GetSession(basePackage.UnitySessionId)` 找到那根 Unity 连接，`SendData` 回去。
>
> 这就是整条链路追踪的核心——**不靠全局 map，靠包自己带着回程地址**。多加一层就多打一个标（比如 `gate_session_id`），回程逐层剥。

**客户端内部（这一步最容易被忽略）：**

> socket 回调在**子线程**上，Unity 的 API 不能直接碰。所以 `NetSocketMgr` 在 Init 时抓住主线程的 `SynchronizationContext`，收到包后 `Post` 回主线程，再 `Events.DispatchNet(protoCode, data)`。
> `EventMgr` 里维护"协议码 → 处理器"的字典，`ProtoHandler` 初始化时把几十个协议号一次性注册进去，收到包就是一次字典查找，然后调对应方法反序列化、更新数据、发事件给 UI。
> 所以完整链路是：**子线程收包 → 拆帧校验解压 → 反序列化 → Post 切主线程 → 按协议码路由 → 业务**。

## 数据流举例（挑一个说，显得你真的跑过）

> 拿位置同步举例：客户端 20Hz（0.05 秒）把 `PositionSyncReq{RoleId, PosX/Y/Z, RotationY}` 发上去；登录服收到后**不落库**，只更新内存里的 `PlayerSceneMgr`，然后遍历同场景其他玩家，给每个人单独组一个 `PositionSyncNtf` 包发出去。
> 敌人是另一条线：客户端只上报"我打了谁"，伤害在服务端算（`EnemyMgr.ProcessAttack`），算完把 `PlayerAttackRet{伤害, 剩血, 是否暴击, 是否死亡}` 广播回去，客户端只负责播表现。**血量只有一个写入口**，客户端没有权限改。

## 追问预案

**Q：为什么不用索引器 `_cmdDic[code]` 取处理器？**
> 踩过坑。索引器取不到会抛 `KeyNotFoundException`，而收包逻辑外面套了一层 `catch`，异常会被当成网络故障直接把玩家**踢下线**——一个没注册的协议码就能踢人。所以改成 `TryGetValue`，并且给单条消息的处理加了 `SafeHandleCommand` 包一层 try-catch，处理出错只记日志，不断连接。

**Q：多线程发送会不会串包？**
> 会，所以要加锁。位置/敌人同步是从服务端 tick 线程发的，和网络线程的发送是并发的，`SendData` 里用 `_sendLock` 把 `socket.Send` 串起来，保证一帧字节连续写出去、不被别的线程插进来。

**Q：为什么高频包不打日志？**
> 位置同步 20Hz × 敌人数 × 玩家数，一条一打直接把控制台刷爆，帧率掉一半。所以 `SendData` 里对 `PositionSync / EnemyPositionSync / SyneAni / PlayerVfx` 这几个协议号直接跳过日志。

**Q：为什么中心服独占数据库？**
> 三个好处：只有一处能写库，不存在多进程抢同一行导致的并发问题；中间层是纯数据通道，加机器就能扛连接；数据库不暴露给网关层，安全边界清楚。
> 代价是所有业务都得穿两跳，延迟多一次转发，而且中心服是单点——真要做生产级得按地图/场景分片，每个分片一个逻辑服，中心服只做账号和跨服。

**Q：断线重连怎么做的？**
> 老实说：`NetClient` 里**写了**重连机制——断线后 3 秒起第一次尝试，之后每 10 秒一次，由 `IsNeedReconn` 开关控制。但这个开关我在客户端**没有真正打开**，现在掉线就是掉线，需要重登。这是已知的待办，不是我做完了的功能。
> 要做完整的话得补三件事：重连成功后重新走登录态校验、把角色状态从服务端全量拉一次（客户端本地状态不可信）、以及断线期间的服务端保活超时（现在服务端 Session 断开就直接移除，没有"保留 N 秒等重连"的窗口）。

**Q：为什么客户端不直连 CenterServer？**
> 一开始是 GateServer → GameServer → CenterServer 三级代理，后来为了减少跳数，把中间两层去掉了，客户端直连 LoginServer，CenterServer 只留 DB 权威。工程里 Gate/Game 的项目还在，但主链路不走它们了。
> 这个演进的好处是链路短、排查快；坏处是 LoginServer 现在既做登录又做玩法权威（房间、敌人 AI、战斗结算），职责变重了，要做大就得重新拆。

## 面试前 10 分钟速记清单

| 要点 | 一句话 |
|---|---|
| 续传粒度 | bundle 级，不是字节级 |
| 缓存一致性 | bundle 原子写入，没下完不进缓存索引 |
| 版本失效 | 缓存 key 带 hash，内容变则 key 变 |
| 顺序 | 先更 catalog，再算下载量 |
| 连接模型 | 客户端↔登录服：一玩家一连接；登录服↔中心服：一共享连接 |
| 帧结构 | 2B 长度 + 1B 压缩 + 2B CRC16 + Protobuf |
| 回程寻址 | 包自带 `unity_session_id`，`SessionMgr` 反查 |
| 线程 | socket 子线程 → `SynchronizationContext.Post` → 主线程 |
| 权威 | 血量/背包/敌人只在服务端算，客户端只上报意图 |

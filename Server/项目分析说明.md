## 一、一句话结论

这是一个 **ARPG（动作角色扮演）多人联机游戏的服务端 Demo**，用 C# / .NET Framework 4.8 写的**分布式多进程服务器集群**：Unity 客户端通过 TCP + Protobuf 连接服务端，完成**注册 → 登录 → 选服 → 创角 → 进场景 → 组队房间 → 实时位置同步 → 服务端权威战斗**的完整链路。

从代码痕迹（目录编号 `03_`/`04_`、大量注释掉的示例代码、`F:\技能实训班\...` 硬编码路径、配套 `一键生成并部署.ps1`）判断，它本质上是**一套游戏服务端开发课程的实训工程**，而不是生产级项目——架构是教科书式的分层代理，但实现上还停留在"能跑通、便于讲解"的阶段。

游戏题材上，从表结构里的"驱动盘"、奖励表里的 `混沌重金属 / 啄木鸟电音 / 原始朋克 / 灵魂摇滚` 可以判断，配套的 Unity 客户端（工程名 `UnderWordYoo`）是一个**仿《绝区零》风格的 ARPG**。

## 三、整体架构

### 3.1 物理拓扑与端口

```
                          ┌─────────────────┐
                          │   MySQL (game)  │
                          └────────┬────────┘
                                   │ SqlSugar
                          ┌────────┴────────┐
                          │  CenterServer   │ 10110   ← 唯一碰数据库的进程
                          │   (CenterApp)   │
                          └───┬─────────┬───┘
                              │         │
              ┌───────────────┘         └───────────────┐
              │                                         │
     ┌────────┴────────┐                      ┌─────────┴────────┐
     │   LoginServer   │ 10120                │  03_GameServer    │ 10130
     │   (LoginApp)    │                      │   (GameApp)       │
     └────────┬────────┘                      └─────────┬─────────┘
              │                                         │
              │                               ┌─────────┴─────────┐
              │                               │  04_GateServer    │ 10140
              │                               │   (GateApp)       │
              │                               └─────────┬─────────┘
              │                                         │
              └──────────────┬──────────────────────────┘
                             │ TCP / Protobuf
                    ┌────────┴────────┐
                    │   Unity Client  │
                    └─────────────────┘
```

所有进程都跑在 `127.0.0.1`（`NetDefine.IPHost`），端口集中在 `Network/Socket/com/NetDefine.cs`：

```csharp
CenterServerPort = 10110;  LoginServerPort = 10120;
GameServerPort   = 10130;  GateServerPort  = 10140;
```

### 3.2 两条请求链路

**链路 A（账号链路，实际在用）**

```
Unity ──► LoginServer(10120) ──► CenterServer(10110) ──► MySQL
Unity ◄── LoginServer(10120) ◄── CenterServer(10110)
```
覆盖：注册、登录、获取服务器列表、创角、开始游戏、保存角色、跳转场景、领取奖励。

**链路 B（网关链路，教学演示，纯转发）**

```
Unity ──► GateServer(10140) ──► GameServer(10130) ──► CenterServer(10110) ──► MySQL
Unity ◄── GateServer(10140) ◄── GameServer(10130) ◄── CenterServer(10110)
```
覆盖：登录游戏服务器、创角、开始游戏、保存角色、跳转场景。**这两个进程不含任何业务逻辑，只做透传。**

> ⚠️ 数据库种子数据里（`CenterServer/DB/DBMgr.cs:36`）写入 `game_server` 表的端口是 `NetDefine.GateServerPort`（10140），也就是说：客户端登录成功后拿到的"游戏服务器地址"指向的是 **GateServer**。但 GateServer 只注册了 5 个命令，**没有**位置同步 / 房间 / 战斗。参见 [第九节 · 问题 1](#问题-1架构割裂两条链路没有合流)。

## 四、各工程职责详解

### 4.1 `Network`（公共类库，无 Main）

被其余 4 个服务端工程和 Unity 客户端**共用**——这就是为什么有一键脚本要把 `Network.dll` 拷进 `Assets/Plugins/Net`。

| 模块 | 文件 | 作用 |
|------|------|------|
| 服务端封装 | `Socket/NetServer.cs` | Bind + Listen(100) + `BeginAccept` 异步接入，每个连接新建一个 `Session` |
| 客户端封装 | `Socket/NetClient.cs` | `BeginConnect` 连上游，支持断线重连（3s 首重连，之后每 10s） |
| 收发基类 | `Socket/com/ServerBase.cs` | 4KB 缓冲、`BeginReceive`、拆包、CRC 校验、发送、错误回包 |
| 会话 | `Socket/com/Session.cs` | 服务端侧的连接对象；**负责在包上打 `UnitySessionId` / `GateSessionId` 标记** |
| 会话管理 | `Socket/com/SessionMgr.cs` | 单例，`Interlocked.Increment` 生成自增 SessionId，提供 `GetSession` / `GetAllSessions` |
| 业务接口 | `Socket/com/IContainer.cs` | `OnInit` / `OnServerCommand`(作为服务端) / `OnClientCommand`(作为客户端) |
| 协议常量 | `Socket/com/NetDefine.cs` | 端口、命令码、`ConnState`、`ClientType` |
| 编解码 | `Socket/com/NetUtils.cs` | `MakeData` / `ParseData` / GZip / CRC16 |
| 工具 | `Common/DataUtils.cs` | 用户名正则、MD5、合法场景名白名单 |
| 协议实体 | `Proto/RequestEntity.cs` (6102 行)<br>`Proto/ResultEntity.cs` (8992 行) | protoc 自动生成，**不要手改** |
| 配置表 | `LubanManager/` | Luban 生成的技能表读取器，当前 `LubanMgr.Instance.init()` 被注释掉 |

### 4.2 `CenterServer`（10110）—— 数据中心 + 唯一数据访问层

- 只作为**服务端**运行（`NetServer`），不连任何上游。
- 启动时 `DBMgr.InitDB()`：连 MySQL、`CreateDatabase()`、CodeFirst 建 4 张表。
- 分层：`Center_LoginCtrl`（协议解析/转发）→ `LoginModle`（纯数据库业务）。
- **所有**账号/角色/背包/奖励的落地逻辑都在这里。

### 4.3 `LoginServer`（10120）—— 事实上的"主游戏服务器"

名字叫 Login，但它承担了远超登录的职责：

| 职责 | 处理类 |
|------|--------|
| 注册/登录/选服/创角/开始游戏/存档/跳转场景/领奖 | 转发给 CenterServer |
| **房间系统**（创建/加入/离开/准备/房主开局） | `Ctrl/RoomMgr.cs` |
| **玩家场景管理 + 位置同步广播** | `Ctrl/PlayerSceneMgr.cs` |
| **敌人生成 + 服务端权威伤害结算** | `Ctrl/EnemyMgr.cs` |
| 动画同步、VFX 同步、敌人位置同步 | `LoginCtrl` + `PlayerSceneMgr` |
| 断线清理（退房间 + 广播离场） | `LoginCtrl.OnSessionDisconnected` |

它启动了两个角色：`NetClient`（连 Center，类型 `LoginServer`）+ `NetServer`（监听 Unity，端口 10120）。

### 4.4 `03_GameServer`（10130）—— 纯转发

`Game_LoginCtrl` 的 5 个 handler 全部是同一行代码：`serverBase._Client.SendData(basePackage);`
回程用 `basePackage.GateSessionId` 找回对应 Session 再回包。

### 4.5 `04_GateServer`（10140）—— 纯转发

`Gate_LoginCtrl` 同样 5 个命令全转发，唯一"业务逻辑"是**跳转场景时校验场景名合法性**（`DataUtils.IsValidScene`）。回程用 `UnitySessionId` 找回 Session。

### 4.6 `Game_Server/`（空壳，未加入解决方案）

`Program.cs` 只有一个空 `Main`，命名空间是 `GM_Server`。这是早期占位目录，**可以删除**（确认 `ARPGDemo_Server.sln` 中确实没有它）。

## 五、网络层实现原理

### 5.1 三层包结构

```
┌────────────┬──────────┬──────────┬──────────────────────┐
│  head(2B)  │ isCom(1B)│  crc(2B) │   data (protobuf)    │
│  消息体长度  │ 是否压缩  │ CRC16校验 │  BasePackage 序列化   │
└────────────┴──────────┴──────────┴──────────────────────┘
             └────────── msgLen = 3 + data.Length ─────────┘
```

- 发送：`NetUtils.MakeData()` —— 超过 200 字节走 GZip 压缩，算 CRC16，拼 2 字节长度头。
- 接收：`ServerBase.OnReceiveCB()` —— 先读 `ushort msgLen`，够一整包就解析，否则跳出循环等待更多数据（**半包处理**）；解析完把残留字节 `Buffer.BlockCopy` 挪到缓冲区头部继续处理（**粘包处理**）。

### 5.2 统一消息信封 `BasePackage`

```protobuf
message BasePackage {
  int32  protoCode       = 1;  // 命令码，决定走哪个 handler
  int32  unitySessionId  = 2;  // 客户端在 Login/Gate 上的会话 ID
  int32  gateSessionId   = 3;  // Gate 在 GameServer 上的会话 ID
  bytes  data            = 4;  // 具体 Req/Ret 序列化后的字节
}
```

**这是整个转发架构的枢纽**。`Session.HandleCommand()` 在分发前根据"我这个进程作为客户端时的类型"自动打标记：

```csharp
if (_Client._clientType == ClientType.LoginServer ||
    _Client._clientType == ClientType.GateServer)
        basePackage.UnitySessionId = SessionId;   // 上游是 Unity
if (_Client._clientType == ClientType.GameServer)
        basePackage.GateSessionId  = SessionId;   // 上游是 Gate
```

下游服务器处理完原样回传，上游凭 SessionId 把响应精准送回原来的那条连接。**请求包即回程信封**，省掉了额外的路由表。

### 5.3 命令分发（命令模式）

```
NetServer/NetClient 收到包
      └─► HandleCommand(basePackage)
            └─► _cmdDic[protoCode] → IContainer
                  ├─ OnServerCommand()  // 我是服务端，处理下游请求
                  └─ OnClientCommand()  // 我是客户端，处理上游响应
```

注册发生在各 `Program.cs` 的 `RegistCommand(cmd, ctrl)`，服务端和客户端各注册一套。

### 5.4 其他机制

- **断线重连**：`NetClient.Disconnect()` 触发 `Timer`（3s 后首次，之后 10s 一次）自动重连上游。
- **断线清理**：`SessionMgr.OnSessionDisconnected` 事件 → `LoginCtrl.OnSessionDisconnected` → 退房间 + 广播 `PlayerLeaveSceneNtf`。
- **高频包免日志**：`ServerBase.SendData()` 对 `CMD_PositionSyncCode` / `CMD_EnemyPositionSyncCode` 跳过日志打印，避免刷屏。
- **错误回包**：统一 `SendError(basePackage, cmdCode)`，回 `CMD_ErrCode` + `ErrMsg`。

## 七、核心业务流程

### 7.1 注册

```
Unity ──RegistReq──► LoginServer.OnRegistHandle
                       ├─ 用户名正则校验 ^[A-Za-z][A-Za-z0-9_]*$
                       ├─ 密码长度 4~16
                       └─ 转发 Center
                              └─► Center_LoginCtrl.OnRegistHandle
                                    └─► LoginModle.RegistAccount()
                                          ├─ 查重 → AcctExist
                                          └─ Insert account 表
Unity ◄──RegistRet── Login.OnRegistResultHandle（失败则 SendError）
```

### 7.2 登录

`LoginModle.Login()`：查账号 → 校验密码 → 校验 `State==1`（否则 `AcctDisable`）→ 用 `LastLoginServerId` 回填 `GameServer` 信息（IP + 端口）→ 返回 `AccountId`。

### 7.3 场景跳转（含状态机校验）

`LoginModle.ChangeScene()` 强制线性推进：

```
StartScene ──► LobbyScene ──► GameScene
```

任何越级跳转返回 `ReqParamError`。`StartGame()` 会把角色场景**重置回 `StartScene`**（保证每次开局从头走）。

### 7.4 开始游戏（下发角色完整数据）

`LoginModle.StartGame()` 组装 `StartGameRet.MainRoleInfo`：
- `RoleBaseInfo`（RoleId、昵称）
- `MainRoleInfo`（AccountId、SceneName、ServerId）
- 从 `role_bag_item` 表读背包，按 `ItemType == "驱动盘"` 分流成 `DriverDiskMap`（带等级/攻防暴击百分比/充能）或 `MaterialMap`

### 7.5 房间系统（`RoomMgr`，内存态）

```
CreateRoom → 分配自增 roomId，创建者即房主，State=Waiting
JoinRoom   → 校验"不在别的房间"+"房间存在"+"房间未开局"，加入后广播 RoomInfoNtf
PlayerReady→ 置位 IsReady，广播 RoomInfoNtf
LeaveRoom  → 移除；房主离开则顺位给第一个人；人空则解散房间
StartGame  → 校验"是房主"+"所有非房主已准备" → State=Playing，广播 RoomStartGameNtf(RoomId, MapId=1)
```

房间数据**完全在内存**，进程重启即丢失，也不落库。

### 7.6 实时位置同步（LoginServer 直接广播）

```
Unity ──PositionSyncReq(roleId, 坐标, 朝向Y, 昵称)──► LoginCtrl.OnPositionSyncHandle
  1. 判断是否首次同步（该 session 尚未绑定 roleId）
  2. PlayerSceneMgr.OnPlayerEnter() + UpdatePosition()   记录/更新
  3. 构造 PositionSyncNtf，广播给同场景其他人
  4. 首次进入时：
     a. 向其他人广播 PlayerEnterSceneNtf（新人来了）
     b. 向新人逐个补发其他人 PlayerEnterSceneNtf（已有谁在）
```

**绕过了 CenterServer**，因为这是高频数据，不能每次都串一遍数据库链路。

### 7.7 战斗（服务端权威）

```
Unity ──PlayerAttackReq(roleId, enemyInstanceId, damage, baojiPercent)──►
   LoginCtrl.OnPlayerAttackHandle
     └─► EnemyMgr.ProcessAttack()
           ├─ 敌人不存在 → EnemyNotExist
           ├─ 已死 → 返回 damage=0 / isDead=true
           ├─ 暴击判定：Random(1,101) <= baojiPercent → damage += Random(200,1500)
           └─ CurrHp -= damage，夹到 0，标记 isDead
     ├─ 回包给攻击者
     └─ 广播给同场景其他人
```

敌人生成同理：`SpawnEnemyReq` → `EnemyMgr.SpawnEnemy()` 分配 `instanceId`（默认 10000 HP）→ 广播 `SpawnEnemyRet` 给场景内所有人。
敌人状态**只在内存**，没有死亡掉落、没有清场逻辑（`RemoveEnemy` / `ClearRoleEnemies` 目前无人调用）。

## 九、发现的问题与风险

### 问题 1：架构割裂，两条链路没有合流 ★ 最关键

- `DBMgr.cs:36` 里种子数据的端口写的是 `GateServerPort(10140)`，即客户端登录后被指向 **GateServer**。
- 但**房间、位置同步、敌人、战斗**这些指令**只注册在 LoginServer(10120)** 的 `NetServer` 上（`LoginServer/Program.cs:31-40`），`Gate_LoginCtrl` 根本没有这些 case，收到会打 `"有没有注册的请求码"`。
- 反过来，LoginServer 上又重复实现了 `CreateRole / StartGame / ChangeScene / SaveRole / LoginGameServer` 的转发，与 Gate→Game 链路**功能重叠**。

判断：`03_`/`04_` 是后加的课程章节（透传演示），而房间与联机同步是更后来才加在 LoginServer 上的（见 `改动说明_房间准备与位置同步.md`）。结果就是**两套入口并存、职责边界模糊**。要么把客户端统一收敛到一条链路，要么明确"LoginServer 管账号+大厅+战斗，Gate/Game 只做章节演示"。

### 问题 2：网络层无并发保护

`SessionMgr._sessionDic`、`PlayerSceneMgr._players`、`RoomMgr._rooms`、`EnemyMgr.enemy_Dict` 都是**普通 Dictionary**，而 TCP 回调跑在 IOCP 线程池上——多个客户端同时发包就是多线程并发读写。轻则状态错乱，重则 Dictionary 内部损坏/死循环。需要加锁或换 `ConcurrentDictionary`，或改成单线程消息循环（推荐后者，也更符合游戏服务器惯例）。

### 问题 3：半包残留会被下一次接收覆盖

`ServerBase.OnReceiveCB()` 处理完粘包后把残留字节 `BlockCopy` 到 `_buffer[0..len]`，紧接着 `BeginReceive()` **仍然从 offset 0 开始写**，会直接覆盖掉刚挪过去的残留数据。结果是：只要出现半包，那部分数据必丢。正确做法是维护读偏移，残留数据后面接着写。

### 问题 4：命令未注册会抛异常而不是优雅降级

`Session.HandleCommand()` 里 `_cmdDic[basePackage.ProtoCode]` 用的是索引器，未注册直接 `KeyNotFoundException`，catch 到后会走 `Disconnect()`——**一个未知命令码就把客户端踢下线**。应该用 `TryGetValue`，并且在 `RegistCommand` 里也把 `Add` 换成索引赋值（重复注册会抛）。

### 问题 5：`GetOtherPlayersInScene` 没有按场景过滤

`PlayerSceneMgr` 的字典是全局的，`GetOtherPlayersInScene(roleId)` 的实现是"返回除自己以外的**所有人**"，`PlayerSceneInfo.MapId` 字段**从未被赋值**。也就是说在 `StartScene` 的玩家会收到 `GameScene` 玩家的位置同步包。需要真正按 `SceneName/MapId` 分组。

### 问题 6：安全与健壮性

- **密码明文存储**：`DataUtils.GetMD5Hash()` 写好了却没用上，`LoginModle` 直接 `accountTable.Password.Equals(req.Password)`。
- 登录无频率限制、无 Token / Session 票据，任意包携带 `roleId` 即可操作他人角色（`SaveRole`、`GetReward` 均未校验归属）。
- 战斗伤害 `damage` 完全由客户端上报，服务端只做了暴击加成，没有校验技能/武器/属性上限——可被改包。
- 高频 `new Random()`：`ProcessAttack` 里每次 new 两个 `Random`，.NET Framework 下默认按时间播种，高并发会得到相同的"随机"序列。应复用静态实例。

### 问题 7：工程杂项

- `Game_Server/` 是空壳目录，未加入解决方案，可清理。
- Luban 配置模块已集成但 `LubanMgr.Instance.init()` 被注释（`CenterServer/Program.cs:15`），且路径硬编码到 `F:\技能实训班\...`，换机器必崩。
- `SaveRoleReq` 的实现只更新了时间戳，随后把该角色背包**全删**（`LoginModle.SaveRole`），`req` 里的实际数据根本没落库 —— 存档功能目前是残的。
- 两个 `Google.Protobuf` 版本并存（Network/Login/Game/Gate 用 3.28.3，CenterServer 用 3.30.0），有版本冲突隐患。

## 十、构建、启动与运行

### 10.1 协议修改流程（一键脚本）

```powershell
.\一键生成并部署.ps1 [-MsBuildPath "...\MSBuild.exe"]
```

1. 用 `protoc.exe` 从 `D:\BaiduNetdiskDownload\课程资料\服务端\proto\proto\*.proto` 生成 C#；
2. 拷贝到 `Network/Proto/`；
3. MSBuild 编译 `Network.csproj`（Debug）；
4. 把 `Network/bin/Debug/*.dll` 覆盖到 `D:\Unity\UnderWordYoo\Assets\Plugins\Net`。

改协议时走脚本，别手改 `RequestEntity.cs` / `ResultEntity.cs`。

### 10.2 启动顺序

```
1. MySQL（确保 localhost:3306 可连，脚本会自建 game 库）
2. CenterServer      ← 必须先起，其它进程会重连等待
3. LoginServer       （连 Center）
4. 03_GameServer     （连 Center）
5. 04_GateServer     （连 GameServer）
6. Unity 客户端
```

进程无启动依赖检查，靠 `NetClient` 的 10s 重连兜底，所以顺序反了也不会崩，只是先刷一堆重连日志。VS 里可用"设置多个启动项目"一次性拉起。

### 10.3 首次运行的手动步骤

1. 建 MySQL 库（脚本自动）+ 确认连接串/账号密码；
2. 往 `game_server` 表插入至少一条服务器记录（代码已注释，需手动）；
3. 如需测试多服务器列表，多插几条。

## 十二、总结

这个项目是**一个教学性质的、功能已跑通的 ARPG 联机服务端骨架**：

- ✅ **做对了**：分层代理架构清晰、`BasePackage` 信封 + SessionId 打标的回程路由设计巧妙、命令模式分发统一、高频数据绕过 DB 直接广播、战斗服务端权威、CRC + 压缩 + 粘包处理形成完整网络层闭环。
- ⚠️ **还差得远**：两条链路职责重叠未合流、无并发保护、半包 bug、密码明文、场景未分区、存档残缺。

**一句话定位**：它完整演示了"一个多人 ARPG 服务端需要哪些进程、怎么分层、怎么同步"，是一份合格的课程样例；但离"能承载真实玩家"还有一轮系统性加固的距离。
